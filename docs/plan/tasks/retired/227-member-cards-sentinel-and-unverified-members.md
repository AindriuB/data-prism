## Goal
Every member that holds the cluster key proves it by publishing a sealed member card, and a member that joins with the wrong key refuses to start instead of producing a stream of tamper counts. When a joined member has no valid card after the grace period, every instance reports it and, under `refuse`, stops serving (design 2.4 d2, OD-8). Data Prism still cannot evict such a member; this is detection and fail closed, not prevention. The cards also carry what task 228 needs, and what the deferred rotation task 229 will need: the accepted key ids, key check values and the highest pause sequence each member has seen.

## Required shape (228 and 286 read these; 229 and 230, which also did, are deferred past 1.0)
- A card holds: member UUID, format version, the cluster key ids this member accepts, a key check value for each configured purpose key (cluster keys and name key now; further purpose keys, such as link keys, through `MemberCards.addPurposeKey(id, material)` before start), the highest pause sequence this member accepted (from a supplier set by 228; zero until then), and a lease end. It is sealed with the member UUID and lease end authenticated.
- `MemberCards`: `verifiedMembers()`, `unverifiedCount()`, `acceptedKeyIdsOfAllVerified()`, `highestReportedPauseSequence()`, `reportPauseSequence(LongSupplier)`. A card is refreshed when half its lease is spent.
- `ClusterSentinel`: at start, read the sentinel; if absent, write it with `putIfAbsent`; act on which held key opens it, per design 4.6. Re-sealing the sentinel on a key advance is task 229's (deferred past 1.0), not this task's.
- `ClusterSecurityStatus`: serving or not, and why (sentinel mismatch, unverified member under `refuse`, key check value mismatch); member count; unverified count. No address, no key id material, no UUID in any text a log or health endpoint shows. Task 228 adds pause freshness to it; task 286 reports it as health.
- `MemberServingGate` closes when the status says not serving, and `PrivacyCluster.servingInstance()` consults it (Context, "Folded in 2026-10-23"). It never blocks the member-card map or the pause-document map, so a member can still prove itself and read or write pause state. While closed, every other sealed operation is refused with the code decided under OD-215-10, so the 233 path carries it to callers. Oversight writes while closed follow OD-215-16.

## Outcome (2026-10-29, 0.8; PR #183, tip 5850fccf, wave/0.8-wave4)
Members publish sealed cards, read a sentinel at join, and fail closed on unverified members. `ClusterSentinel` reads the sentinel at start (writing it with `putIfAbsent` under `current`, never `next`); a member whose keys do not open it refuses with the new `CLUSTER_KEY_MISMATCH`, leaves the cluster and publishes no card. `MemberCards` publishes a sealed card (UUID, format version, accepted key ids, key check values, highest pause sequence, lease end), refreshes it at half the lease and judges every live member's card; `ClusterSecurityStatus` says serving or not and why, and `MemberServingGate` closes on it. `PrivacyCluster.servingInstance()` is the gated accessor; `instance()` is unchanged. The approval store, budget, caller-rate limiter, identity cache and re-identification index use `servingInstance()`. `ClusterMembership` no longer accepts `localhost` as a keyless address. Base: `origin/wave/0.8-wave4`. Hazelcast module 561 tests, core 1,140.

Owner and orchestrator decisions. OD-W6-7: grace applies only to members that join after this instance is already serving; a member already present and unverified when this instance starts gets no grace, until a judgement of this instance has come out serving once. OD-W6-8 (a): the grace clock is cluster-wide, as this instance sees it, not per member UUID, so a fresh UUID cannot reset it; its reset clause is superseded. OD-W6-9 (a), 2026-10-28: the clock resets only after zero unverified members have been seen continuously for at least GRACE (`clearSince` set at the first zero look, cleared whenever a look shows an unverified member, reset once `now - clearSince >= GRACE`; a failed look changes neither). Orchestrator call: per-wrapper `MemberCards` plus a shared `Declarations` object in the instance's user context, accepted in place of one shared card object. A shared object would have had to carry one wrapper's settings, environment and executor for all, while the guarantee is about the content of the card; every wrapper publishes the union of key check values and the highest pause sequence ever reported (monotonic).

What review changed. The gate belongs to the instance, not the first wrapper: `PrivacyCluster` keeps the set of live keyed wrappers, and the registered sealer and `servingInstance()` both ask the same aggregate (at least one live wrapper, all serving; the caller must itself be live). A wrapper joins the live set only after `cards.start()` succeeds. Any exception during a look leaves the member not serving (`CARDS_UNAVAILABLE`). No cluster call is made while the card lock is held, writes are bounded and not started while one is outstanding, and the sentinel write has the same in-flight guard. A purpose key added during a write bumps a generation so the next tick republishes. Round 3's rewrite of `judge` dropped the pruning of `rejected` and `mismatchesCounted` for departed members, so fresh-UUID outsiders with large planted strings grew the heap without bound; it is restored with tests.

CI. `ClusterLockTimeoutTest.aHeldRateLimiterLockRefusesAndCountsNothing` flaked because of this branch: the first member now writes its sentinel and card before the second joins, so partitions migrate after the join, and `isClusterSafe()` was false right after `TestMembers.pair` in 104 of 104 probes; the test now waits, bounded, for partitions to settle (`ClusterLockTimeoutTest` and `HazelcastHardeningTest` were widened into Owns). The Java 21 failure was real: Hazelcast replies to a migration with `PartitionStateVersionMismatchException` when the member list changes mid-migration, our serialisation filter rejected it, and the migration waited for its timeout. It is now allowed by exact name in `ALLOWED_CLASSES`; a test reproduces the hang. The exception was latent on the wave branch, and 227 makes it likelier.

External review P1: the bound-address checks read the advertised address, so a real wildcard bind advertising 127.0.0.1 passed (fail open). Both checks now use `PrivacyCluster.listeningAddresses`, the local address of each open server-socket channel in the member's registry (read from Hazelcast 5.7.0 internals); anything unreadable gives an empty set, which is refused. Tests use real instances. Not testable here: a keyed member on a real 10.x interface.

Deviations. `ArchitectureTest` (its `Sealer.open` rule also allows `MemberCards` and `ClusterSentinel`), `ServingInstanceArchitectureTest` allows a fifth class, `IdentityMaps`. `PrivacyCluster.memberCards()` returns `Optional`. `addPurposeKey` is allowed after start and republishes at once. The duplicate-UUID test waits 5 s for a join that must not happen. Not done: the 222 follow-ups (`UNSAFE_HAZELCAST_SERIALIZATION` rename or note, ancestor-package over-refusal, the embedded-path blacklist message) and the `UNSEALED_CLUSTER_STATE` excuse for a verified member.

For 213 and 284: store code of an embedder's own should call `servingInstance()`; a hand-built serialisation filter must also list `PartitionStateVersionMismatchException` (use `PrivacyCluster.requiredSerializationFilter()`); a keyless member's `localAddress` and `publicAddress` must be a literal loopback address (`127.x.x.x` or `::1`), and `localhost` is refused with `MISSING_CLUSTER_KEY` (`INVALID_CLUSTER_INTERFACE` when keyed).
