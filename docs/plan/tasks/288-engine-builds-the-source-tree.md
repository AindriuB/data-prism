## Goal
The scrubber applies a holding field's policy to whatever tree it is given and descends only into JSON objects. Today that tree is whatever Jackson writes, so any Jackson feature that changes the written shape (`@JsonValue`, a custom serializer, an array shape, an object id, a type wrapper, a `@JsonProperty` name swap) can move a sensitive value out from under its own classification. Make that impossible instead of detecting it: the engine walks the record itself, reading each component's value by its own rules and writing it under the component's own name. Jackson is handed only JDK scalar values, never a value whose graph can hold a user class or a record.

## The walker (the rules `SourceTree.of(Object)` follows)
- **Root.** A `JsonNode` root is normalised (below). Any other root must be a record (`SOURCE_MODEL_NOT_A_RECORD` otherwise, as today).
- **Generic records before the position rule.** A record class that declares type parameters is refused with `SOURCE_MODEL_GENERIC` wherever it is met, after the map-value rule and before the array-level-two and position rules ("Position rule", Order), so `SourceModelsTest`'s `Envelope` behind an `Object` component (:741-744) keeps its code (and gets the path `$.any`, see "Changed expectations").
- **Record.** An `ObjectNode` with one property per record component, in declaration order, named by the component's name, each value read from the component's private field (Decisions). No other property is written. Jackson annotations on the record, its components, accessors, other methods or interfaces have no effect (290 refuses them at startup for the author's sake, not for safety).
- **Unwrap order and declared types.** The walker carries the declared type of each position down from the component's generic type. At each level it applies, in this order: an `Optional`, `OptionalInt`, `OptionalLong` or `OptionalDouble` is unwrapped and its type argument becomes the declared type (empty is `null`, D-173-1); a JDK `Collection` or an array other than `byte[]` and `char[]` becomes an `ArrayNode` and its element type becomes the declared type of each element; a JDK `Map` becomes an `ObjectNode` and its value type the declared type of each value. So `List<Optional<Leaf>>` declares `Leaf` for each unwrapped element and is accepted, and `Optional<List<Leaf>>` and `Optional<Leaf[]>` likewise. A type variable or wildcard is read by its upper bound; an unbounded one, a raw type and `Object` declare nothing. A declared `Iterable<T>`, or a declared JDK interface that extends it (`Collection<T>`, `List<T>`, `Set<T>`, `Queue<T>`, `Deque<T>` and the like), is walkable by its type argument at startup, and at scrub time its runtime value is handled by its runtime class: a JDK `Collection` is walked with `T` as each element's declared type; any other runtime class goes through the leaf rule, so `Path` is a leaf and an `Iterable` Jackson writes as a container is refused. So `@NonSensitive Iterable<String> tags`, which starts today, still starts and still scrubs.
- **Position rule.** A non-null record value is accepted only where the declared type, after that unwrapping, is exactly that record class. Anything else is refused with `SOURCE_MODEL_RECORD_NOT_DECLARED`: `Object`, an interface, `java.lang.Record`, an unbounded type variable or wildcard, a raw collection, and a runtime class that differs from the declared one (heap pollution). Records are final, so `List<? extends Contact>` is exact. A record that is a map value is refused with `SOURCE_MODEL_MAP_OF_RECORD`, and a record at array level two or deeper (counted as `SourceModels.recordBeyondFirstArray` counts) with `SOURCE_MODEL_NESTED_COLLECTION_OF_RECORD`: the startup codes, now also at scrub time. **Map values (internal review of c47bd335..4859aa40, P3).** The map-value rule applies to any record whose path passes through a map value, at any depth below it: the value itself, or an element of a collection, array or `Optional` inside it, however deeply nested, and whatever the map's declared value type. This is what startup does: `SourceModels.walk` refuses a map whose value type argument contains a record anywhere (`containsRecord(arguments[1])`, `SourceModels.java:263-265` on wave4), so `Map<String, List<Leaf>>` and `Map<String, List<List<Leaf>>>` give `SOURCE_MODEL_MAP_OF_RECORD` at startup (`SourceModelsTest.java:724-725` and :814-816) and now give the same code at scrub time. A record in a heap-polluted `Map<String, String>`, or below a map held at an `Object` position, is `SOURCE_MODEL_MAP_OF_RECORD` too (the heap-polluted map under Acceptance, "Read failures"). **Order (review of c47bd335, P3; changed at the review of c47bd335..4859aa40 so that it agrees with startup):** for a non-null record value the walker checks, in this order, the map-value rule, then the generic-record rule, then the array-level-two rule, and only then the position rule (`SOURCE_MODEL_RECORD_NOT_DECLARED`). So a generic record as a map value (`Map<String, Envelope<Leaf>>`) is `SOURCE_MODEL_MAP_OF_RECORD` at scrub time, as at startup, where `containsRecord` sees the record before `walk` reaches the generic; a generic record anywhere else is `SOURCE_MODEL_GENERIC`, as at startup, where `walk` refuses it before `recordBeyondFirstArray` runs (`SourceModels.java:229-241`). The array-level-two rule counts declared levels, as `recordBeyondFirstArray` does (`SourceModels.java:330-350` on wave4), so it applies where the declared type puts the record at level two or deeper; an `Object` or `List<Object>` position declares no level, so `Object=[[Leaf]]` and `List<Object>=[[Leaf]]` stay `SOURCE_MODEL_RECORD_NOT_DECLARED`, as pinned under "Changed expectations". **Path (D4).** A `SOURCE_MODEL_GENERIC` refusal at scrub time carries the path of the position where the generic record sits, like 288's other scrub-time refusals (`SourceModelsTest.java:741-744` expects `$.any`, see "Changed expectations"); at startup the path is `$`. **Note on the order.** The order matches startup for a single offending record. When the offence is nested inside a record that is itself at a refused position, startup reports the inner code and scrub reports the outer one. Example: `List<List<Holder>>` with a `Map<String, Leaf>` component in `Holder` gives `SOURCE_MODEL_MAP_OF_RECORD` at startup and `SOURCE_MODEL_NESTED_COLLECTION_OF_RECORD` at scrub. Both refuse.
- **Containers.** A user subclass of a collection or map is refused (`SOURCE_MODEL_NOT_A_RECORD`), as `refuseContainer` does today, by its class and before any of its methods is called. A collection or map whose class passes the JDK-class test is iterated as on the base commit, a JDK view or wrapper included (OD-288-2 (b)); what a wrapper delegates to is the residual under "Trust model". Map keys: each key's runtime class passes `SourceModels.refuseKey`, whose JDK test is the JDK-class test below; an enum key is written by `name()`, as enum values are; every other key is written as the reader writes that JDK key type today.
- **Reference and holder types.** Besides the four `Optional` types, which are unwrapped, every JDK reference or holder type is refused with `SOURCE_MODEL_NOT_A_RECORD`, at startup and at scrub time: `java.util.concurrent.atomic.AtomicReference`, `AtomicReferenceArray`, `AtomicStampedReference`, `AtomicMarkableReference`, `java.lang.ref.Reference` and its subclasses, `ThreadLocal`, `java.util.concurrent.Future`, and any other JDK class Jackson writes with a reference-type, bean, container or map serializer that the walker does not handle itself. `AtomicInteger`, `AtomicLong` and `AtomicBoolean` hold no object and are scalar leaves.
- **Single-use types (re-review P3).** `java.util.stream.BaseStream` and its subtypes, `Iterator`, `Spliterator` and `Enumeration` can be consumed only once. `SourceValues.prohibited` (`DefaultContextOrchestrator.java:387`) runs before `scrub` (:390), so if either read one, the other would get `IllegalStateException`, outside the per-source catch. These types are refused with `SOURCE_MODEL_NOT_A_RECORD` by type, at startup on the declared type and at scrub on the runtime class, before anything iterates or serializes them. The lenient walk records the position and does not touch the value.
- **Two readers (re-review P2).** Startup builds record serializers to inspect them: `SourceModels.walk` calls `SourceTree.refuseIfReadByGetters` on each record (`SourceModels.java:244`), and `refuseForeignProperties` reads a record's bean serializer until 290 replaces it. The parity oracle also needs Jackson's plain output. A guard that refuses records would break all three. So `SourceTree` builds two private readers from one shared configuration method. Both stay inside `SourceTree`, the class `ArchitectureTest.ONLY_DESIGNATED_CLASSES_CREATE_MAPPERS` (:108-117 on wave4) already allows, so that rule is unchanged.
  - **The leaf reader**, guarded (below). It is the only reader whose `valueToTree` main code calls, and only from the walker's leaf method.
  - **The inspecting reader**, unguarded. Main code uses it only to look serializers up (`refuseIfReadByGetters`, `refuseForeignProperties`, the leaf rule's container test); it never writes a value with it. The parity oracle reaches it through one package-private test seam, `referenceTree(Object)`, that no main class calls.
  - `SourceTreeReadersArchitectureTest` (ArchUnit) pins this:
    - no main class other than the walker calls the leaf method, and no main class calls `referenceTree`;
    - the inspecting reader's field is read only by `refuseIfReadByGetters`, the foreign-property lookup, the leaf rule's container test and `referenceTree`;
    - inside `SourceTree`, no serialising method of `ObjectMapper`, `ObjectWriter` or `SerializationContext` (`valueToTree`, `convertValue`, every `writeValue*`, `writeValueAsString` and `writeValueAsBytes` included, `writer()` or `writerFor()` followed by any `write*`, `serializeValue`) is called anywhere except in the leaf method, on the guarded reader, and in `referenceTree`.

    So the scrub path has no unguarded way to write a value. The test has negative fixtures for each forbidden call, so it cannot go blind to one.
- **Leaves.** Enums are written by `name()`. Any other value is a leaf, delegated to the leaf reader's `valueToTree`, only if all of these hold:
  - its class passes the JDK-class test ("No direct call on a user class"), and is not a record, an enum, a collection, a map, an array other than `byte[]` and `char[]`, a reference or holder type, or a single-use type (above), and is not one the inspecting reader writes with a container, iterator or map serializer. So an `Iterable` that Jackson writes as a scalar, such as `java.nio.file.Path` (written as its URI text), is a leaf, and the guard and the scalar-result check still protect it;
  - it is not a class the reader would read by getters (`Throwable`, `java.awt.Point`): the surviving part of `refuseSerializer`, called directly;
  - the **leaf guard** passes. The leaf reader keeps a serializer modifier and an annotation introspector, the roles of today's `RecordsOnly` and `ClassLevelSerializers`, reduced to the leaf path: while a serializer is built for any class, they refuse every record, every class not loaded by the bootstrap or platform loader, every class-level serializer annotation, and every bean, reference-type or container serializer.   - the result is one of: a scalar node (string, number, boolean or binary), a null node, or a `POJONode` whose held object's class is exactly `byte[]` (`getClass() == byte[].class`, checked before anything else is called on it). On Jackson 3.1.8 the leaf reader turns a `byte[]` leaf into such a `POJONode`, not a `BinaryNode` (probed at the review of 1ccd3ef9). Any other `POJONode`, an object or an array refuses with `SOURCE_MODEL_NOT_A_RECORD`.

- **`JsonNode` normalisation (root and components).** Every `JsonNode` the walker meets, at the root or in a component, map value or collection element, is checked and copied node by node: the walker checks one source node's class, creates that node's copy and attaches it to the result, and only then reads the node's children, each checked and copied the same way. Each container node's content is read through one iteration of its own (`properties()` for an `ObjectNode`, one iterator for an `ArrayNode`), and nothing of it is read again. The walker creates every node through a factory it owns, `JsonNodeFactory.instance` (or the leaf reader's own factory, itself exactly `JsonNodeFactory`), never through the source node: no `deepCopy()`, no `objectNode()`, `arrayNode()` or other creating method of a source node, and nothing that consults a source node's `_nodeFactory`, which the adapter may have made a user subclass of `JsonNodeFactory`. The source tree may contain only Jackson's own container and scalar node classes, exactly: `ObjectNode`, `ArrayNode`, `StringNode`, the numeric nodes, `BooleanNode`, `NullNode` and `BinaryNode`, each from Jackson's code source and not a subclass. The class is compared with `getClass() ==` before any method of the node is called, at every level, so an overriding method of a subclass (`properties()`, `size()`, `iterator()`, `get(...)`) is never entered. Anything else is refused with `SOURCE_MODEL_FOREIGN_NODE`: a `POJONode` whatever it holds, any other embedded-object node, a `MissingNode` inside a container, or a node class from outside Jackson, a subclass of a Jackson node class included. Inside a `DecimalNode` or a `BigIntegerNode` (each already matched by exact class), the held number's class is checked the same way before any of its methods is called: `decimalValue().getClass() == BigDecimal.class` and `bigIntegerValue().getClass() == BigInteger.class` (`getClass()` is final, and the two node getters are Jackson's). Otherwise the result equals (`JsonNode.equals`) what `SourceTree.of` returns on the base commit. No node of the source tree is placed in the result by reference, and a `BinaryNode`'s copy holds a copy of its bytes ("One tree"). `ConfiguredJsonScrubbingEngine`'s parsed trees contain only these classes, so configured JSON sources are unaffected.

- **Read failures (internal review of 1ccd3ef9, P2).** Every read the walker makes of the source value is wrapped, in `of` and in the lenient walk alike: a field-handle read, a holder getter, an `Optional` read, a node's class check and its `properties()` or iteration, a collection's `iterator()`, `hasNext()` and `next()`, a map's entry iteration, `getKey()` and `getValue()`, an enum's `name()`, the JDK-class test, the container and getter tests, and the leaf reader's `valueToTree` with its result check. - **Trust model (OD-288-3 (b), owner, 2026-10-27).**
  - Source-adapter code, including the source model's classes and every object the adapter builds, is trusted deployer code. It runs in-process with the server's rights, so a hostile adapter is out of scope: it could read the raw values without the walker's help.
  - Upstream data is untrusted, but it cannot create user subclasses. Only adapter code can put an instance of a user class, or a JDK object carrying a user callback, into a source value.
  - So the walker defends against mistakes in trusted code (an overriding getter, an annotation, a swapped accessor, a pre-built tree with a Java object in it), not against an adapter that means harm. The guarantees below are what it keeps; the residual is stated under Out of scope.
- **Guarantee 1: no direct call on a user class (external review of 732ddec6, P2).** Neither `of` nor the lenient walk calls a method directly on an object whose class code outside the JDK and Jackson supplies. One rule decides which objects the walk may call methods on: **an object's methods are called only when its runtime class is exactly one of the JDK or Jackson classes this brief names for that purpose (`getClass() == X.class`), or when that class is final and every method called on it is final, or, for a leaf, a container (a collection or map) or a map key, when it passes the JDK-class test below.** `instanceof`, `isAssignableFrom` and "loaded by the bootstrap loader" alone do not satisfy it. The rule applies to every value the walk meets in the source: the root, a component's value, an element, a map key or value, a holder's content and a node. It does not apply to the helper objects that an allowed JDK or Jackson call returns: an iterator, an entry set, a `Map.Entry`, a key set or a values view. Those are used as returned. `ObjectNode.properties()` returns the backing map's own entry set, and iterating an `ArrayNode` or a JDK wrapper returns the backing list's own iterator, unwrapped; when the adapter built that map or list from a class of its own, these helpers are its code, which is the residual under "Trust model" (Out of scope), not a breach of this rule. Every value such a helper hands back is checked by this rule before the walker calls anything on it. **One more exemption (internal review of c47bd335..4859aa40, P3): a throwable the walk caught.** The walker calls `getCause()` on a throwable that a read threw, which can be the adapter's own exception class with an overriding `getCause()`, to look for its own `PrivacyRefusedException` ("Cause chains"); it also calls the final `getClass()` on it for the log line. Nothing else is called on it: not `getMessage()`, `toString()` or `getStackTrace()`. The `getCause()` calls are bounded (32 steps or a repeat), and a throw from one is a read failure; a `getCause()` that blocks is the residual under Out of scope. Applied:
  - **Records:** components are read from fields through `privateLookupIn` handles, never through accessors, `equals`, `hashCode` or `toString`; nothing else is called on a record. Enums: only `name()`, which is final.
  - **`Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`:** final classes, read by `isPresent()`, `get()`, `getAsInt()`, `getAsLong()` and `getAsDouble()`.
  - **`JsonNode`s:** the exact-class check in "`JsonNode` normalisation" comes before any call, and so does the number-class check inside `DecimalNode` and `BigIntegerNode`.
  - **Containers:** a user subclass is refused by class before any of its methods is called; a collection or map that passes the JDK-class test is iterated (OD-288-2 (b)), and what its iteration returns is used as returned (above).
  - **Leaves, containers and map keys, the JDK-class test** (by loader, not by exact class): the class is loaded by the bootstrap or platform loader, is not a dynamic proxy class (`Proxy.isProxyClass`), and is not hidden (`Class.isHidden`). A proxy's every method runs the caller's `InvocationHandler`, so calling it is a direct call into user code, and a proxy for JDK interfaces can be defined by the bootstrap loader. A hidden class (a lambda, including one the JDK defines in `java.base` around a user function, such as `Comparator.comparing(userFn)`) is not a type the walker knows how to read. Every check that consults Jackson (the container test, the getter test) runs only after this test passes, so no serializer is built for a user class at scrub time.
  - **The lenient walk's holders:** the allowlist under "`SourceValues.prohibited`" is stated in these terms.

  Configuration is outside the walk and is called as today: the profile's `FieldMetadataResolver` and policy beans.
- **Guarantee 2: one tree (verified against this design, 2026-10-27).** On the scrub path, the source value is read exactly once. `JsonTreeScrubbingEngine.scrub` calls `SourceTree.of` once (`:119` on wave4), applies the profile's policies to the tree it returns, and builds the output from that tree; nothing in `scrub` reads the source value again. For that to hold, `of` returns a tree that only the walker has referenced: every node in it is created during that call, by the walker (through its own factory, never a source node's) or by the leaf reader, and no node or array is shared with the source value (a `JsonNode` met in the value is copied node by node as it is checked, each container's content read through one iteration; a `BinaryNode` is built over a copy of the bytes; a `byte[]` leaf is handed to the leaf reader as a copy, OD-288-4 (a)). So each part of the source is read once, code running during or after the walk, a user callback included, cannot change a node that has already been checked, and what is scrubbed is exactly what the output is built from. Other walks of the same value exist, and none feeds the output:
  - **`SourceValues.prohibited`** walks the value separately, before `scrub` (`DefaultContextOrchestrator.java:387` and `:390` on wave4). Its set is the oracle of `RawValueLeakValidator`, which looks for one source's raw values in another source's output. A value can be missing from that set, which weakens the cross-source oracle, in two ways: it changes between the two walks (a user callback, the residual), or, once task 291 lands, the lenient walk stops at the node cap, which a plain large collection with no user callback can reach, and later values are not collected. In the second case `of` refuses that source too (`SOURCE_TREE_TOO_LARGE`), so the source itself releases nothing; only another source emitting one of the uncollected raw values goes uncaught by `RawValueLeakValidator`. It cannot weaken the scrub: the scrubbed output is built from the one tree `of` produced, under each field's own policy.
  - **`NamespaceCorrelationService.correlate`** calls `SourceTree.of` again on the raw record (`:59` on wave4). Its findings carry source names, counts and fixed reasons, never a value (`compare`, `:93-140`), so a changed value can change which sources are reported as agreeing, not what is released. If `of` refuses there (a callback that throws only on a later read), the refusal propagates and the request fails closed; nothing is released.
  - **`ConfiguredJsonScrubbingEngine.scrub`** (`data-prism-connectors-rest`, `:95-99` on wave4) reads a configured JSON source's body twice besides `engine.scrub` (:98): `ConfiguredJsonNestedLeafShapeGuard.check` (:95) and `SourceValues.prohibited` (:99), both before or after the one tree is built and neither feeding the output. The orchestrator reads the same payload twice more, as it reads every source record: its own `SourceValues.prohibited` (`DefaultContextOrchestrator.java:387`) and `NamespaceCorrelationService.correlate` (:59, called from `DefaultContextOrchestrator.java:198`), neither feeding the output either. So the body is read five times, of which only `engine.scrub`'s read builds the output. That is safe only because of where the body comes from: `ConfiguredJsonPayload` is a package-private record (`ConfiguredJsonPayload.java:18`), and main code builds it in one place, `ConfiguredJsonDataSourceAdapter.fetch` (:52), from the `ObjectNode` Jackson parsed out of the HTTP response body. No adapter code holds that tree, and it is made of Jackson's own nodes over Jackson's own maps and lists, so it cannot change between the reads. A change that lets code other than the parser build a `ConfiguredJsonPayload` or supply its body (a public constructor, a body passed in by an adapter) opens these walks to the residual and must make all five reads one, or derive the other four from the one tree `engine.scrub` builds.
- **Guarantee 3:** `prohibited` never throws, except a `VirtualMachineError` ("Read failures"), and stays bounded in depth ("`SourceValues.prohibited`", below). This task does not bound it in size; task 291 adds the node cap (OD-288-6 decided (b)).
- **Caching.** Field handles are cached per record class in a `ClassValue` or equivalent that keeps no class loader reachable beyond the class's own lifetime.

## `SourceValues.prohibited` (lenient walk)
`prohibited` never throws for this task's refusals (kept from 270), nor for anything a read throws, save a `VirtualMachineError` ("Read failures", above: every read is caught per position, not only the holder getters). It runs outside `DefaultContextOrchestrator.fetchAndScrub`'s per-source `try` (`:387` on wave4); the refusal comes from `scrubber.scrub` inside it (`:390`), so only that source is refused. It reads the tree through a lenient mode of the same walker:
- Where `of` would refuse with `SOURCE_MODEL_RECORD_NOT_DECLARED`, `SOURCE_MODEL_MAP_OF_RECORD`, `SOURCE_MODEL_NESTED_COLLECTION_OF_RECORD`, `SOURCE_TREE_NOT_COMPONENT_EXACT` or `SOURCE_MODEL_FOREIGN_NODE`, it walks the value by its own runtime class, and every scalar under it is prohibited (a foreign node's own content is not read).
- **Unreadable records, the fail-closed rule.** Where field access is denied, every scalar reachable through the accessors is prohibited. That is not the whole set: with swapped accessors, a value held only in a field that no accessor returns is not reachable at all. `SourceModels.require` refuses an unreadable record class at startup, but only for the adapter's declared `responseType()` and the records it reaches. `SourceFanOut` does not check that a returned root record is of that declared type (corrected after the re-review of f7e30ac1). So an unreadable record can reach `prohibited` in two cases: an embedder skipped `require` (plain Java), or an adapter returned a different `@LlmExposedModel` record than it declared. The residual is exact. It needs all of: the module path, a model package not opened to `data-prism-core`, a root record class other than the declared one, and swapped explicit accessors. Its effect: a value held only in a field is missing from the prohibited set, so another source emitting the same raw value is not caught by `RawValueLeakValidator`. The refused source itself emits nothing. A root-type check fits neither `SourceTree` nor `SourceValues`, which do not know the declared type, and `SourceFanOut` is 246's. It is filed under Out of scope as a follow-up. `docs/extending.md` (290) states that plain-Java embedders must call `SourceModels.require`. The scrub of that source refuses with `SOURCE_MODEL_NOT_READABLE`, so the source's own output never carries the value. A readable record is always read by field, in the lenient walk as in `of`, so its every value is collected.
- **Bounded.** The lenient walk uses the same depth count as `of`, including record levels. At the bound it stops descending and returns what it has: the scrub of that source refuses with `TOO_DEEP`, so nothing under the bound is emitted by that source. It is iterative or bounded, never recursion without a limit, so no `StackOverflowError` from the walk itself can escape `prohibited`. The bound is on depth only: a container whose iteration never ends (a residual callback) is not stopped by it here; task 291 adds the node cap that stops it (OD-288-6 (b)).
- **No refusal escapes (re-review P3).** `prohibited` throws for none of the walker's refusals, pre-existing ones included (`SOURCE_MODEL_NOT_A_RECORD`, `SOURCE_MODEL_GENERIC`). This resolves the follow-up 270 had left out of scope. For each refused position it records the position and prohibits every scalar under it that it can reach without serialising anything:
  - records by field, and containers and maps under the same class rule as `of` ("Containers"; a user subclass is prohibited-unknown, never iterated; a JDK collection or map is iterated, OD-288-2 (b));
  - the content of a holder type, only from this closed allowlist, walked by the same rules. The allowlist obeys "No direct call on a user class": a holder is read only when its runtime class is **exactly** one of the classes named here (`getClass() == X.class`), or the class is final and every method called on it is final. Checked on JDK 25 with `javap`:

    | Holder | Class final? | Methods called | Those methods final? | Condition to read |
    |---|---|---|---|---|
    | `AtomicReference` | no | `get()` | yes | exact class |
    | `AtomicReferenceArray` | no | `length()`, `get(int)` | yes | exact class |
    | `AtomicStampedReference` | no | `getReference()` | **no** | exact class |
    | `AtomicMarkableReference` | no | `getReference()` | **no** | exact class |
    | `Optional` | yes | `isPresent()`, `get()` | (final class) | none beyond the class |
    | `OptionalInt`, `OptionalLong`, `OptionalDouble` | yes | `isPresent()`, `getAsInt()`, `getAsLong()`, `getAsDouble()` | (final class) | none beyond the class |
    | `CompletableFuture` | no | `state()`, then `resultNow()` | **no** | exact class, and `state() == Future.State.SUCCESS` |
    | `FutureTask` | no | `state()`, then `resultNow()` | **no** | exact class, and `state() == Future.State.SUCCESS` |

    The four atomic classes and the two Futures are read by exact class: the rule is uniform, so the two `AtomicReference` classes, whose getters happen to be final, are not a special case. `ForkJoinTask` is removed from the allowlist: it is abstract, so no instance has that exact class, and its `resultNow()` calls the abstract `getRawResult()`, which a subclass supplies. A JDK subclass of a listed class (`CompletableFuture.minimalCompletionStage()`'s class, `ForkJoinTask`'s JDK subclasses) is not on the list either, and is prohibited-unknown. A Future that is running, failed or cancelled is not read: no `get()`, no waiting, nothing that throws `CancellationException` or `ExecutionException`.
  - **A subclass of a listed holder, and any holder not on the list,** is prohibited-unknown, as an unreadable value already is here: none of its methods is called, not even `state()` or `isDone()` (the default `Future.state()` calls `isDone()` and then `get()`), nothing is thrown, and its position is recorded with nothing under it added to the set. A user class implementing `Future` is one such holder.
  
  Nothing else is read. That covers `ThreadLocal` (whose `get()` would read the orchestrator's own thread and could run a `withInitial` supplier), `java.lang.ref.Reference` and its subclasses (no `get()`, and nothing reconstructed through them), the internals of a user class, the content of a `POJONode`, a holder that is not exactly a listed class, and single-use values. Each such position is recorded as prohibited-unknown: nothing under it is added to the set, and the scrub of that source refuses inside the per-source `try`, so the source emits nothing. Every getter call on the allowlist is wrapped, as every other read is ("Read failures"): an `Exception` (checked included) or an `Error` other than `VirtualMachineError` from it is caught, and the position becomes prohibited-unknown. That catch is a second line only: it cannot stop a blocking call, which is why the exact-class rule, not the catch, is what keeps direct calls on user classes out. So nothing but a `VirtualMachineError` escapes `prohibited`, and it never blocks on a method of a user class. A user callback reached through a JDK object the adapter built can still stall it or exhaust memory (task 291's node cap stops a walk growing past 1,000,000 nodes and refuses that source, but it is not a memory limit: memory can still run out before the cap is reached, and a single large value counts as one node); that is the residual under Out of scope.

- `extra` left unannotated: the profile's `unclassified` setting decides the field. Under the bundled DEFAULT profile (`FAIL_REQUEST`) the scrub refuses with `UNDECLARED_FIELD` at `$.extra`; the other settings apply to it as to any unannotated field;
- `extra` marked `@NonSensitive`: the profile's `unclassified` setting decides the whole map. Under DEFAULT (`FAIL_REQUEST`) it refuses with `UNCLASSIFIED_STRUCTURE`; `REDACT_AND_WARN` replaces the map with the marker; `PASS_THROUGH_UNSAFE` releases the map whole, keys included.

For a record source, the undeclared-key handling becomes unreachable. It stays reachable through `JsonNode` roots: configured JSON sources, and a test resolver that exposes the tree.
- **(a) Refuse it; rework the fixtures. Decided.** Each of the nine either becomes a `JsonNode`-root source (with `ConfiguredJsonFieldMetadataResolver` or a test resolver that exposes the tree), so that its undeclared-key assertions still mean something, or keeps a record with a `Map<String, Object>` component and asserts the outcomes above instead. The Outcome says which for each. Cost: an adopter's open root model loses its extra keys' per-key handling. They must classify the holding map field as a whole, or move to a configured JSON source.
- **(b) Keep it, by the engine's own rule. Not chosen.** The walker flattens one `Map<String, ?>` component marked `@JsonAnyGetter` into its record's object, writing keys as for any map and refusing a key equal to a component name. The keys then reach the undeclared-key handling at the record's level, as today. 290 exempts `@JsonAnyGetter` on such a component. The nine fixtures pass unmodified. Cost: the engine reads one Jackson annotation, and the collision rule is a new check to get right.
- **Recommendation: (a).** It is what the owner listed, it leaves no Jackson annotation with meaning, and the collision case (an extra key named like a `@NonSensitive` component) is a value swap that (a) cannot express at all. Today's behaviour on that collision is itself unchecked (270, Out of scope).
- **Decided: (a), by the owner, 2026-10-27.**

- **Residual of the trust model (OD-288-3 (b), owner, 2026-10-27), documented, not closed.** A user callback reached through a JDK object that the adapter built runs during `of` and during the lenient walk. The known carriers: an `ObjectNode` or `ArrayNode` built over a user map or list; a `URL` with a user `URLStreamHandler`; a `Calendar` with a user `TimeZone`; `LongAccumulator` and `DoubleAccumulator`; `TreeSet` and `ConcurrentSkipListSet` sub-views that call a user comparator; the `Collections.unmodifiable*` wrappers and the other JDK views and wrappers (OD-288-2 (b)); JDK lambdas that wrap user functions; and the `getCause()` of an exception class the adapter throws from such an object, which the walker calls to look for its own refusal (Guarantee 1's exemption; at most 32 calls per caught throwable). Such a callback can stall a request or exhaust the process's memory (an iterator that never ends grows the tree until an `OutOfMemoryError`, which is process-wide, not one request's; the base commit's `valueToTree` does the same). After task 291, the node cap stops a walk growing past 1,000,000 nodes and refuses that source with `SOURCE_TREE_TOO_LARGE`; it is not a memory limit — a walk can still exhaust a small or busy heap before reaching the cap, concurrent walks add up, and a single large value counts as one node, as does each value a callback yields, because the cap counts positions, not bytes, and the read copies binary arrays (OD-288-4 (a)). Such a callback can make a read throw (that source is refused, "Read failures"), and can make `prohibited` collect a different value than `of` read (weakening the cross-source oracle, "One tree"). It cannot leak data: the scrubbed output is built from the one tree `of` produced, every value in it under its own field's policy. Closing it has no fixed boundary (OD-288-3); the owner chose to state the trust model instead. 290 documents the model and this residual for users (`docs/architecture.md` and the `docs/extending.md` box).
