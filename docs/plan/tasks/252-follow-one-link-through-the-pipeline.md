## Goal
`follow` takes one sealed link and reads its target on the holder's behalf. It must re-check everything a fresh call checks (P5), refuse every invalid link with one uniform answer while the real reason goes to the audit only (P4, T7), lock out a principal that grinds forged links (OD-8), resolve a translated link at follow time through the bounded invoker (OD-R2), charge every read and resolver call before making it, and pass the target's answer through the same scrub and validation as any read. No path from the adapter reaches the caller without the engine.

Supply the issue time from the clock and the link id from a random source. Expect `LINK_KEY_UNRESOLVED` from `forScope` when the current key is down (`attemptCounterKey` is removed by 269).
- From 269 (OD-269-1 to 4 decided by the owner and coordinator 2026-10-22, OD-269-5 pending; brief revised 2026-10-24, after review 5): open every link through the gate. `LinkAttemptGate.open(token, binding, accepted)` is the one call. It checks the inputs (a null or empty token, a null binding or `accepted`, an empty or over-bound id: `Invalid(MALFORMED)`, uncounted), then `lockState` (a locked principal gets `Exhausted(LOCKED)` before the token is opened, valid links included). It then opens the token and records a counted refusal atomically. It returns `Proceed(opened)`, `Invalid(reason)` or `Exhausted(cause)`; the cause is `LOCKED`, `OVER_LIMIT`, `CEILING`, `LIMITER_UNAVAILABLE` or `OPEN_FAILED`. It never throws, and it treats a null answer from the limiter or the codec as a refusal. Answer the client with `decision.clientCode()`: `LINK_INVALID`, `LINK_ATTEMPTS_EXHAUSTED`, or the OD-269-5 placeholder for an outage, which is `LINK_ATTEMPTS_EXHAUSTED` for now. Never compute the code yourself. Write `decision.auditValue()` (`REFUSED:LINK_<REASON>` or `REFUSED:LINK_ATTEMPTS_<CAUSE>`) under the call's `link` disposition key. Architecture rules forbid calling or referencing `LinkCodec.open` or the limiter outside `core.link`, and forbid any `core.link` class outside `data-prism-core`; `mcp` may not depend on `core.link` at all. The post-authentication checks this task makes after `Proceed` (target permitted, relation declared, payload consistency) are uncounted and never touch the limiter. The guarantee is at most `limit` `LINK_INVALID` answers per window, and at most `limit` plus the attempts in flight for guesses that can reveal a success. At the ceiling a subject that is not stored is never locked (OD-269-3, accepted by the owner).
- From the external review of PR #154, rounds 1-4 (2026-10-23): at the tool boundary an MCP client may send "" meaning "no link", and the codec counts "" as `MALFORMED`. **Closed 2026-10-23 (coordinator decision, built by 269):** `LinkAttemptGate.open` treats a null or empty token as `Invalid(MALFORMED)`, uncounted, without calling the codec, so a confused agent cannot lock itself out. This task passes the argument through unchanged and needs no mapping of its own.

## Acceptance
- [ ] Tests are written first and fail on the base commit; the Outcome names them.
- [ ] Order of checks (the first three run inside one `LinkAttemptGate.open` call, 269): binding bounds; limiter (a locked principal gets `LINK_ATTEMPTS_EXHAUSTED` for any link, valid ones included, and nothing is read); codec verification; then, after authentication, target still permitted (`SourceVisibility`), relation still declared (target still accepts the namespace; for a translated link, the named resolver bean still exists), and payload consistency. Every failure returns the same result with code `LINK_INVALID` and text `The link is not valid.`; results for each reason in the closed set are byte-identical apart from `correlationId`; the audit decision is `DENY:LINK_INVALID` with `link` = `REFUSED:LINK_<REASON>`. Counted reasons are recorded by the gate; others never are.
- [ ] `FollowLimiterTest`, one row per gate outcome through stub limiter and opener states: `LOCKED`, `OVER_LIMIT`, `CEILING`, `LIMITER_UNAVAILABLE` (`UNAVAILABLE`, null, or a throw) and `OPEN_FAILED` (a throw, or null). Each row asserts that the result's code is `decision.clientCode()`, that nothing is read (adapter stub at zero calls), and that the audit record's `link` disposition is exactly `REFUSED:LINK_ATTEMPTS_<CAUSE>`, with decision `DENY:` plus the client code. An empty-string link is `LINK_INVALID`, audited `REFUSED:LINK_MALFORMED`, and leaves the counter untouched. Mutants: audit one value for every cause; count `""`.
- [ ] A direct link reads the target once with the sealed key, through the shared fetch, scrub and validate steps (a stub validator that refuses yields a refusal, proving no bypass). The request to the adapter carries the key namespace (`DataRequest.withKeyNamespace`).
- [ ] A translated link calls the resolver through `ResolverInvoker` with `dataprism.key-resolvers.max-targets` and the timeout, charges `budget-cost` before the call, then reads each returned key once, each charged before its read; keys are read and `items` are ordered by ascending keyed fingerprint, never by the real key. More than the cap is `RESOLVER_FAILED` with no read; `more` sets `itemsTruncated`; an empty result is `NO_DATA`; each failure reason gives `RESOLVER_FAILED` and its metric, and never falls back to a direct read, another resolver or the untranslated key.
- [ ] Outer status and items follow OD-9: `ANSWERED` if any item answered, otherwise `NO_DATA`, a shared status, or `FAILED`; a refused item is omitted and audited under `<target>[<i>]:<refused>` as `REFUSED:<code>`; every answered item refused refuses the call with the first refused code. Tests cover each mix of sealed-links item 24.
- [ ] Budget: an unaffordable resolver call or read is not made; exhausted before the first read refuses with `SCOPE_READ_BUDGET`; exhausted part-way returns the items read and `itemsTruncated`. Each read is charged to the read key's own subject counter (OD-08-15 (a)) and always to the scope total.
- [ ] The followed result is the `get_entity_context` envelope with exactly one entry keyed by the target label, `entity` only for `ANSWERED`, its own one-step `_links` (251's rules), and `names` recorded as 247 does. `RESOLVER_FAILED` is added to `SourceOutcome.Status` and `source-status-codes.txt` together.
- [ ] Leak tests: the link token, the chained key and every resolver input and output key are in no response, log line, metric, exception or audit record, in plain or encoded form, on success and on every failure path. `follow` never reaches `ScopeIdentityIndex.subjectFor` (existing architecture rule still passes).
- [ ] `LinkTimingSoakTest` measures expired, authenticated-but-not-permitted and forged tokens and asserts they are not separable beyond a tolerance stated in the test; it is excluded from `./mvnw verify` by tag.
- [ ] Before merge, a whole-component hunt for concurrency and privacy-boundary defects covers `follow`, the limiter path and the budget path; each finding is fixed or filed and named in the Outcome.
- [ ] `./mvnw -B verify` (full reactor) passes.
