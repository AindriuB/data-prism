## Goal
288's walkers are bounded in depth but not in size, so a source value that never ends (a JDK collection over an adapter's own iterator that never stops) grows the tree until the process runs out of memory, which fails every concurrent request rather than one source. Cap the number of nodes either walk reads from one source value, refuse that source alone with `SOURCE_TREE_TOO_LARGE` when `of` reaches it, and stop the lenient walk at the cap without throwing. The cap bounds how many positions a walk visits, not how much memory it takes: a single large value still counts one.

## The cap
- **The constant.** `SourceRecordWalker.MAX_NODES = 1_000_000`, package-private, `static final`, one per source value: each call of `SourceTree.of(Object)` and each call of `SourceValues.prohibited` starts its own count at zero.
- **What it bounds, honestly (external review of 47ef9fbe, P2).** `MAX_NODES` bounds the number of positions one walk of one source value visits, and so the number of `next()` calls it makes. It does not bound memory, of the walk or of the process, and no figure in bytes is claimed for it. The walk's extra memory is the per-node overhead (one `JsonNode` or set entry per position) times the node count, plus the per-value copies 288 requires, which scale with the size of the values, not with the count: each `byte[]` leaf is copied by the walker (`clone()`, OD-288-4 (a)) and, on Jackson 3.1.8, again by the leaf reader (`Arrays.copyOfRange` in `TreeBuildingGenerator.writeBinary`), so up to two copies of each array; each `BinaryNode` met in a `JsonNode` is copied with a copy of its bytes ("One tree", OD-288-4 (a)). 288 mandates no copy of a `String`, `BigDecimal` or `BigInteger`: they are immutable, and a copied `StringNode`, `DecimalNode` or `BigIntegerNode` is a new node that may hold the same instance, so it costs node overhead only. The leaf reader's own output (a `char[]` written as a `String`, a leaf such as `Path` written as its text) and the scalars the lenient walk adds to its set also scale with the values' size. Those values are usually ones the adapter already holds, but a callback in the residual can create them as it is read (an endless iterator that yields a fresh large array each time), so a single large value, or up to `MAX_NODES` of them, can still exhaust the process's memory while counting one node each. A process runs one walk per source in each concurrent request, so these costs add up across sources and requests. If a walk reaches the cap, the cap stops it growing further and refuses that source; it is not a memory limit (a walk can still exhaust a small or busy heap before reaching the cap, and concurrent walks add up), and the wording below says so: per source value and node count, in the docs, and "a source whose value holds", in the CHANGELOG.
- **What counts.** Every position the walk enters counts one before anything is read from it: the root, each record, each component value, each collection or array element, each map entry, each `JsonNode` (container or scalar), each leaf, and each `null`. The count is checked before the read that would enter a new position, so for an iterator the walker calls `hasNext()` and, if the next position would exceed the cap, stops before calling `next()`. So `next()` is called at most `MAX_NODES` times in one walk, whatever the value holds.
- **In `of`.** Entering a position beyond the cap throws `PrivacyRefusedException` with code `SOURCE_TREE_TOO_LARGE` (the public constant `SourceTree.SOURCE_TREE_TOO_LARGE`), path `$`, and the fixed message "the source value has more nodes than the engine reads". The message carries no count, no class name and no value. It is the walker's own refusal, so 288's per-position read wrap ("Read failures") passes it through unchanged and never turns it into `SOURCE_VALUE_READ_FAILED`. It runs inside the orchestrator's per-source `try`, so that source alone is `REFUSED:SOURCE_TREE_TOO_LARGE` and the other sources still answer.
- **In the lenient walk.** Reaching the cap stops the whole walk: the position where it stopped is recorded as prohibited-unknown, everything already added stays in the set, nothing more is read (no sibling, no parent's next element), and `prohibited` returns. It throws nothing, as 288's Guarantee 3 requires.
- **What the stop costs the cross-source oracle.** The values after the stop are not in the prohibited set, so `RawValueLeakValidator` does not catch another source that emits one of them. Unlike the trust-model residual, this needs no user callback: a plain JDK collection with more than `MAX_NODES` elements reaches the cap. The source itself releases nothing, because `of` counts the same positions and refuses it with `SOURCE_TREE_TOO_LARGE`. 288's Guarantee 2 says the same.
- **Order with the other bounds.** Whichever of `TOO_DEEP` and `SOURCE_TREE_TOO_LARGE` the walk reaches first is the refusal. 288's other refusals are unchanged.
- **Configured JSON sources.** Their bodies pass through the same walks (288, "`JsonNode` normalisation"; `ConfiguredJsonScrubbingEngine.java:95-99`), so a body over the cap is refused the same way. The engine is not edited.

## Out of scope
- Making the cap a property, or deriving it from `maxResponseBytes` (option (c), not chosen).
- A cap on bytes, on string or array length, or on time spent in a callback (adding one needs an owner decision): a callback that blocks still stalls the request, and a single large value can still exhaust memory (288's residual, which stays documented).
- `JsonTreeScrubbingEngine` (271's in wave 5), `ConfiguredJsonScrubbingEngine`, `DefaultContextOrchestrator`, `RequestLimits` and `LimitsProperties`: the cap lives in the walker only.
- `docs/plan/design/contract-register.md` (290 writes the row; 211 owns the file in this wave) and `docs/migration-0.8.md` (261).
- Any other wording in the trust-model paragraph or the `docs/extending.md` box (290).
- The values a capped lenient walk does not collect ("What the stop costs the cross-source oracle"): the source is refused, and no further walk is added to collect them.
- A value that is under the cap when scrubbed but over it when `NamespaceCorrelationService.correlate` reads it again (only possible through a residual callback): that refusal fails the request closed, as 288 states for any refusal there.
