- [ ] `docs/multiple-instances.md` opens its cluster section with "Multi-member: trusted network only. Approvals and counters are unsealed." It then says exactly what is and is not protected in 1.0:
  - Sealed: the pause document (228). A deleted, forged or replayed document cannot lift a pause; an absent or stale one means everything is paused.
  - Verified: members (227). A member with the wrong key refuses to start (`CLUSTER_KEY_MISMATCH`). A joined member without a valid card is counted, and under the default `refuse` every instance stops serving and readiness goes `DOWN` (286) until it leaves. Data Prism cannot evict it.
  - Sealed: identity and re-identification entries (225). Values are envelopes under the cluster key; subject ids appear in the cluster only inside them, and forged entries never change a returned value. Deleted re-identification entries are lost for good. They are sealed under the current key only: rotation (229) is deferred, so a cluster-key change is a planned full restart that empties both maps, and pseudonyms issued before it can no longer be re-identified.
  - Not sealed: approvals and their claims and pending slots, and the budget and caller-rate counters. Anyone who can reach the member port can read them and can write them. Map keys are keyed names (223), so a reader learns no scope or subject from a key, but values are plain.
  - Required on `tcp-ip` and `kubernetes`: `dataprism.hazelcast.trusted-network: true` and a private `member.interface` (or a `member.trusted-ranges` entry), with the refusals `MISSING_TRUSTED_NETWORK`, `PUBLIC_MEMBER_INTERFACE` and `INVALID_TRUSTED_RANGE` (284), and the plain-Java declaration (287). The member port must still be isolated by the deployer (firewall, NetworkPolicy or a private network), because member traffic is not encrypted.
  - Links and page links are refused on joining members (`MISSING_SHARED_LINK_LIMITER`, 255), so `list_sources` answers on one page there.
  - Cluster security for untrusted networks is planned after 1.0, and the page says so, without dates.
- [ ] `docs/eu-ai-act.md`'s shared-cluster paragraph no longer says that losing a pause flag's owner and backup reopens the paused path (after 228, an absent pause document means everything is paused). It says, in one or two sentences, that the pause is sealed and members are verified, that identity and re-identification entries are sealed, that approvals and counters are not, that a cluster is supported on a trusted network only, and it links to `docs/multiple-instances.md` for the detail.
- [ ] `docs/migration-0.8.md` and `CHANGELOG.md` (`[Unreleased]`, Added) describe `PrivacyCluster.servingInstance()` (227): Data Prism's stores use it, it refuses with `CLUSTER_OPERATION_REFUSED` while the member is not serving, `instance()` is unchanged and ungated, and an embedder's own cluster-backed store should move to `servingInstance()` to be refused with them.
- [ ] Wherever `trusted-network` is documented (`docs/multiple-instances.md`, `docs/migration-0.8.md`), it is stated as the operator's isolation assertion, in 284's words: only Data Prism members can reach the member port; it is not inferred from a private address. The Kubernetes example's member-port NetworkPolicy is shown as what makes the assertion true there, with its limit: it admits any pod labelled `app: data-prism`, so "trusted" means anyone who can create pods in that namespace, and the page recommends a dedicated namespace. The page also says the assertion holds only with a network plugin that enforces NetworkPolicy (flannel and kind's default do not) and with no `hostNetwork` pods in the namespace, which bypass it (third external review of PR #164). The multi-instance Compose file is described as a local demo only: the assertion holds only on a Linux Docker engine where cross-network routing to the member port has been checked, and not on OrbStack or Docker Desktop, which may route to it across networks (second external review of PR #164).
- [ ] The trusted-network guardrail is described as what it is: an operator assertion plus a bind and advertised-address check (284, 287). The docs say it does not stop an untrusted host from joining and does not make a cluster safe on a network the operator does not control. No page calls the cluster "secured" or "protected" by it (external review of PR #164, 164-3). 284's one-sentence insertion at the top of the cluster section of `docs/multiple-instances.md` is replaced by, or merged into, the full text here.
- [ ] `docs/migration-0.8.md` and `CHANGELOG.md` (`[Unreleased]`, Breaking) state that a `tcp-ip` or `kubernetes` member now needs `dataprism.hazelcast.trusted-network: true` and a private interface, with a before-and-after configuration, and the plain-Java declaration (287's Outcome) with a before-and-after call.
