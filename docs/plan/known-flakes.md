# Known test flakes

Shared list of tests that have failed without a code defect, with what is known. Status:

- `fixed`: the cause is found and the change is named.
- `open`: not fixed, or never reproduced and no cause found.
- `watch`: conditional; no failure seen.

A test that passed with no change is never `fixed`. Last updated by the record of 263 Part A (2026-11-11). Symptoms come from CI
logs of failed runs (`gh run view <id> --log-failed`) unless a row says otherwise.

Cause: the paused caller's id lock has a real lease of five times its timeout (1.5 s at 300 ms), and the test reached its first assertion after the lease had run out on a slow runner, so the second member's `create` took the lock instead of being refused. Reproduced by a 2 s sleep before that assertion. Change: the paused caller's store gets a 1 s timeout (5 s lease); the second member keeps 300 ms. |

| `MemberCardTest.aResumeOrEndScopeThroughAServingWrapperIsRefusedWhileAnotherWrapperOfTheInstanceDoesNotServe` | `Expecting code to raise a throwable` at :715 (CI run 42041178892). | `fixed`. Reproduced by a temporary latch holding the executor look while the test faulted on its own thread. Cause found, a test defect: the grace clock starts at the first look that sees the intruder (`MemberCards.java:1286-1290`), and the only look before the test's `GRACE+1s` advance is the membership-event `lookSoon` on the executor, which the test never waits for. | `StdioParseErrorLeakTest.errorWrongType` | `assertGuardRefused:100` on `build (25)` (CI run 43049590251 attempt 1, PR #243, 2026-11-11); the rerun passed. | `fixed` by task 309 (PR #249, 2026-11-11). Cause, a test defect with a security edge: the test calls `Process.destroy()`, which on JDK 25 also closes the parent's stderr stream (`ProcessImpl.destroy`), so unread stderr is lost and the drain swallows `Stream closed`. Reproduced 2 in 200 in a Linux JDK 25 container with one CPU, 5 of 5 with a forced 100 ms stderr lag. The same teardown in `StdioSdkLogPinTest.runChild` and `StdioParseErrorLeakTest.assertNoLeak` lets a `doesNotContain(SENTINEL)` check pass on truncated stderr. No product leak found. Fix: `toHandle().destroy()`, `waitFor` 10 s with `destroyForcibly` fallback, join both readers to end of stream, fail on a reader `IOException` (5 of 5 pass; 20 consecutive runs pass). With a 100 ms stderr lag the base teardown fails `errorWrongType` and the fixed one passes. Not related to 305. |
